### Agent Definition Files

Each agent YAML defines: tools permission (**the `enforce` switch can force it: when enforce=true, filter by the allowed whitelist / disallowed blacklist — blocked tools' schemas are not uploaded to the LLM + execution entry interception; enforce=false (default) stays backward-compatible with full injection**), behavior, skills preload list.

⚙️ Current state: **chat_agent has enforce=true with a 32-entry allowlist — read_file / search_files / search_in_file / grep / glob, web_search / fetch_url / browser_navigate, 14 read-only GitHub MCP methods and 10 read-only Chrome DevTools MCP methods; write, execute, download and clarify tools are denied and their schemas filtered out. code_agent has enforce=true with an empty allowlist, which means no filtering at all (every tool is granted, new tools included) — its restriction comes entirely from the permission chain**; other agents remain declarative (enforce off, full injection unaffected).

### Prompt structure and its contract test

`code_agent_prompt.md` is the code agent's full system prompt. Sections in file order: CKB mechanism (detection, on-demand reading, build-mode constraints, build exemptions, MCP fallback, incremental sync), tool restriction order (`powershell` / `execute_code` as last resort, gated on three sufficiency conditions), supreme principle, tool-name rules, language policy (reply in the user's language), life-or-death rules (tool calling, tool-name integrity, output-execution consistency, iteration completion, truthfulness), general rules (file reading, failure-retry with backoff and a 60s budget, file operations, code editing), available tools, core responsibilities, general workflow (task list, clarification, review, code writing, debugging phases, LSP checks with a compile-based fallback), general techniques, output specifications.

Severity wording: 13 headings carry the `[MUST]` suffix — CKB build-mode constraints, supreme principle, output-execution consistency, truthfulness, general rules, task-list updates, requirement clarification, requirement review, code quality, handoff document, HTML comment loop, debugging process, LSP checks. No other severity vocabulary exists: `(must)`, `(mandatory rule)`, `(important!)`, and `(violation = failure)` do not occur anywhere in the file.

`tests/test_code_agent_prompt_contract.py` pins the prompt to the runtime: required sections present, every tool named in the prompt granted by the YAML allowlist or owned by an MCP server in `.mcp.json`, no ghost entry in the allowlist, no forced single-language rule, no ambiguous severity marker, the `[MUST]` heading count fixed at 13, and the CKB exemptions / MCP fallback / retry budget still documented. The tool universe is the schema set in `agent_core/tool_definitions.py`, which the handler-side table in `agent_core/tool_impl/registry.py` mirrors exactly.

### Notes

5. **Single-agent architecture — there is no sub-agent orchestration.** Agent switching is handled by the `_current_agent` global in server.py; there is no multi-agent routing or delegation layer
6. **The system prompt is rebuilt on every `chat_stream` call**, not cache-stable (memory is hash-cached but paths/usernote change each time)
7. **search_files execution model ** — runs via `asyncio.to_thread` (keeps the event loop free) + directory pruning + streaming chunked search (`_stream_search`, 1MB chunks, constant memory, supports arbitrarily large files) + binary double-filter (extension blacklist + NUL byte detection) + 30s time budget + 200-result cap; constants defined at the top of `tool_executor_impl.py` (`_SEARCH_*`). `find_files` uses a simpler unpruned scan (lower risk — it only matches file names)
8. **grep/git output decoding** — `_tool_grep`/`_tool_git_status`/`_tool_git_log`/`_tool_git_diff` use `encoding='utf-8', errors='replace'`; tasklist/taskkill output is localized GBK and stays on the locale codec. Subprocess calls specify encoding explicitly
9. **Intermittent empty-output turn end (model-side behavior; detection + one auto-retry)** — the model can end its turn at the "thinking → acting" junction (reasoning finishes but no tool call and no closing text; occasionally `｜｜DSML｜｜` markers leak). Signature: finish_reason=stop with an intact reasoning stream and zero content — the model itself chose to end its turn at that boundary; an intermittent model-side behavior, not a network drop and not a client-side failure. Backend handling (three layers): ① log persistence (gateway/log_setup.py → `{PEBBLE_HOME}/logs/backend.log`) ② per-round finish_reason capture + stream-end log (stop/length/None distinguishable) ③ auto-retry once on a suspicious end (`_is_suspicious_stream_end`: length truncation or no text output; retry = echo current output + inject continuation prompt; limited to once per turn). Retry construction (agent_chat_service_v2.py): the assistant message is echoed only when content is non-empty — the continuation prompt alone keeps the request legal; if a retry request is rejected by the API, the turn is accepted as complete with a warning (in_suspicious_retry / graceful_abort flags) rather than raising. Triage entry: search backend.log for "Suspicious stream end" / "stream end: finish_reason=". In practice the turn usually recovers via the retry; otherwise it ends cleanly.
10. **Agent tool-policy enforcement (chat_agent enabled)** — chat_agent hard whitelist (only read_file/search_files/edit_file/write_file): ① schema layer — `_get_tools_definition(agent_def)` calls `filter_tools_for_agent`; non-whitelisted tools (incl. MCP) are not described to the LLM ② execution layer — `tool_executor_impl.execute` entry calls `check_agent_tool_policy` ③ effective only for enforce=true agents (currently chat_agent only; other agents keep full injection) ④ implemented in agent_loader.py ⑤ restart the backend after editing YAML (agent cache is process-level, no mtime invalidation)
