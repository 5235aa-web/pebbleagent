| github | status / repos / repo / contents / commits / commit / issues / pulls / file / local / activity / pullfiles. Every method runs in the thread pool — `ws_server` routes any `github.*` through `asyncio.to_thread`, because a REST round trip is 100ms–2s and a synchronous call would freeze the whole WebSocket loop, stalling streaming replies and permission prompts along with it. The PAT is read from the user-level `.mcp.json` github entry (only `GITHUB_*` variables are considered, and the bundled `ghp_xxxx` placeholder is rejected) so the panel never asks for a credential the MCP server already carries; it is never returned to the renderer, and `status` reports only login, avatar and quota. Responses are cached by ETag — a 304 replays the stored body — and every reply carries `rate` so the panel can show the hourly quota. `force: true` skips that cache for one request, which is what the panel's refresh button sends; the flag rides on a `threading.local` set at the top of `handle` rather than on a parameter, because a refresh has to reach every `_fetch` a handler makes and threading it through eight functions for one button would be noise; the cache dict and its trim order are guarded by a lock that is never held across the request, so concurrent fetches still overlap. `repo` accepts only `owner/name` (anything path-shaped is refused before it reaches a URL), `contents` rejects `..` segments, and 401 / 403 / 404 / rate-limit map to readable messages instead of raw status codes. `local` reads the active project's `.git/config` for the origin remote and `.git/HEAD` for the branch — never spawning git for either, since parsing one ini line is a far smaller surface — and falls back to `srv._get_current_project_root()` when the caller omits the path, because the renderer's project registry can arrive after the first status answer. `ahead` and `dirty` are the two that shell out — `git rev-list --count HEAD --not --remotes` and `git status --porcelain` — both read-only, `GIT_TERMINAL_PROMPT=0`, 3s timeout, any failure answering 0 rather than an error. `dirty` exists because `ahead` alone is 0 for an afternoon of uncommitted edits, which made the panel claim "in sync" while twelve files were modified: the question the strip answers is "what of mine is not on GitHub yet", and that covers the working tree as well as the branch. `activity` proxies `/stats/commit_activity` and passes GitHub's 202 through as `pending` instead of pretending the repository has no commits; the client retries. `pullfiles` caps at 100 files and marks `truncated` when the cap is hit or when any file arrives without a patch, which is how GitHub signals a binary or oversized diff. `commit` takes only a hex sha of 7 to 40 characters — GitHub would also resolve a branch or tag name there, and that is a ref this panel has no business fetching — and returns `stats` plus per-file patches; the commit *listing* endpoint carries neither, which is why the panel shows no `+/-` on a row until it is opened. `file` returns the raw blob through `Accept: application/vnd.github.raw` — no base64 round trip — and refuses three shapes rather than letting the panel render garbage: a body over `_MAX_FILE_BYTES`, a `..` segment, and a NUL byte in the first 8 KB (flagged `binary: true` with the text left empty). An oversized blob arrives as 403 with a JSON body naming the 1 MB limit, so that case is matched before the generic explainer, which would otherwise blame the token scope and send someone to reissue a working PAT |
| system | open_url (http and https only; anything else is refused before the shell sees it. Windows uses `os.startfile`, other platforms `webbrowser.open`. The link comes from model output, so the protocol check is the whole security boundary) |

> Single-file revert (`session.file_revert`): records are matched by normalized absolute path equality. One click reverts the newest active snapshot of that file and returns `remaining` (active snapshots left for the file). A failed restore leaves the record active and returns the failure message. The RPC runs in the thread pool. `session.file_changes` returns `active_count` per file.
