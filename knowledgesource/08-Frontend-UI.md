### Notes

4. **Provider loading**: `loadProvidersFromBackend()` is called during app startup (2026-07)
8. **ask_user_question second-call freeze pitfall (fixed 2026-07-31)**: with multiple asks in one turn, the frontend's `clarify.request` replaces `streamingMessage.questionCard` each time (id changes, render position doesn't); without a `:key` binding on AskQuestionCard, Vue reuses the component instance and the old `sb=true` state masks the new question → the UI shows only the tool card "waiting for output" and the new question is invisible. **Fix: MessageBubble.vue binds `:key="message.questionCard.id"` on both AskQuestionCard usages**. Note when troubleshooting: a cancelled tool's empty `input` in execution_order **does NOT mean the LLM returned empty arguments** (the tool_orchestrator cancellation event once omitted input; fixed 2026-07-31)
9. **Render-order scramble after refresh (fixed 2026-07-31)**: dual-DB asymmetry — `agent_chat.db`'s `execution_order` column stores the full R/X/T interleaved order, but `sessions.db`'s `messages.tool_calls` column once stored only a bare tool array (`tool_executions`). The frontend restores preferentially from sessions.db (`resumeSession → convertBackendMessages`); a bare tool array triggered `text_fallback` pushed to the end + `reasoning_fallback` unshifted to the front → body text after tool cards, reasoning first. **Fix: server.py saves assistant messages using `chat_completed_data.execution_order` (full order); tool_executions is only a fallback**. Old data cannot be recovered (order info lost); to verify the true order, cross-check agent_chat.db's execution_order
12. **Image detail level (added 2026-09-06)**: ① the frontend InputArea selector Auto/Low/Orig shows only with image attachments; Auto = field not sent (documented as equivalent to original); ② detail flows AttachmentItem.detail → sendMessage serialization → server.py pass-through → service whitelist injection into the image_url block (invalid values silently ignored, fall back to the original image); ③ detail is a per-request parameter, not persisted (images never enter the DB); ④ low = 512×512 downscale, saves tokens; prefer it for OCR/screenshot scenarios; ⑤ the global selector applies to all images in the request (the docs support per-image detail; the current implementation uses one level for all)
13. **Images vanishing across sessions pitfall (fixed 2026-09-06, plan A)**: ① root cause: images don't enter the DB (service intentionally burns them per-request) + sessions.db messages has no attachments column + resume logic "backend wholesale overwrites the cache when converted.length>0" → images permanently lost after switching windows/refresh, and the localStorage cache was overwritten by the no-image version too; ② fix: mergeCachedAttachments() merges attachments of image-carrying user messages from the localStorage cache back into converted, matched precisely by messageId (not positional alignment, preventing tail-message misattachment); ③ known limitation: depends on local localStorage — clearing cache / another browser / another device still loses images (plan B: backend DB persistence + server-side image replay in context would fix it fully; not implemented); ④ deeper leftover: even when the UI image is back, the model context has no image (DB-restored history has no image_url block); asking about the image later, the model won't know — needs backend replay of images into context (plan B scope)
14. **ask_user_question card "resurrection" defect (fixed 2026-09-06, trio)**: ① root-cause chain: clarify.request mounts the card with state defaulting to undefined → submit only changes the component-local sb, never writes back message.questionCard.state → chat_completed freezes it (L265 transfers questionCard) → history/streaming template branch switch unloads and rebuilds the component → props.state still undefined → the awaiting card resurrects and can be submitted repeatedly; ② frontend fix: gateway markQuestionState() sets the message card's state to answered/skipped the instant submit/skip events fire (scans both streaming and history); AskQuestionCard adds watch(p.state) to sync local sb/sk; ③ backend guard: _submit_clarify_answer validates request_id == QuestionManager pending id; no pending / id mismatch is ignored — repeated submissions of old cards cannot pollute the next ask's waiting event (QuestionManager is a global singleton + answers key hardcoded "0" (changed 2026-10-15 to the multi-question dual channel, see item 23) + request_id originally unused were the contributing conditions); ④ the event's request_id and the QuestionManager pending id are the same uuid (service L1860-1879 set_pending_questions), so the guard doesn't misfire on normal answers; ⑤ the refresh-recovery path (gateway L132) already rebuilt answered/skipped, consistent with this fix
15. **Question-card inline rendering revamp (2026-09-06)**: the card moved from the message-level questionCard field to an inline question element inside executionOrder — when clarify.request arrives, the tail of order is exactly the ask_user_question tool card (tool.call_streaming enters the stream first), so the push lands right after the tool card; after answering, the agent's continued text/tool output appends below the element, and the card stays in place instead of being pinned to the message end; chat_completed no longer migrates questionCard (already inline in eo); the recovery path splices a read-only card after the ask tool item in execOrder; MessageBubble renders the question branch + hasQInline dedup (legacy questionCard fallback for old messages); markQuestionState dual-carrier (inline element + message-level). Note: the ask tool's output is still persisted in the DB; the question element is a pure frontend concept and does not enter the DB; recovery rebuilds from output.questions; the change is frontend-only, event protocol unchanged
16. **Streaming-highlight incremental rendering (added 2026-09-12)**: ① background: full hljs re-highlighting + DOM replacement per chunk is O(n²) and can fall behind the LLM generation rate on large write_file payloads (events pile up, UI waits at "processing"); ② approach: during streaming, ToolExecutionCard delegates to the utils/incrementalHighlight.ts engine — prefix region cached (recomputed only when S advances) + window region recomputed O(W) per chunk, a forged prefix reproduces the cut-point state (hljs prefix determinism guarantees visual equivalence); zero mechanism reduction (per-chunk real-time rendering, highlighting preserved, no throttling); ③ whitelist: python/javascript/typescript/json/bash/plaintext; **css removed** (hljs's css strings are "fully-matching", the forged prefix doesn't work in unclosed streaming states); ④ known limitation: syntax-level nesting (hljs-params nesting depth of unclosed brackets) may show slight visual differences in intermediate states for "malformed text + specific cut points" — the completion state rebuilds fully and corrects it; differential tests pass on real-code scenarios; ⑤ troubleshooting: when the engine is disabled/supported=false it falls back to full rendering (symptom = performance regression but correct display); check ToolExecutionCard's incActive state; ⑥ when extending languages: the scanner must handle "cross-window escape skipping" (the scanStateAt first-char skip logic) and pass differential tests
19. **Conversation-list time semantics (2026-09-25)**: ① a list entry's date = the conversation's latest message time (last row's created_at by sort_order in the messages table) — not sessions.updated_at (polluted by renames/previews and missing assistant replies), not started_at (fixed creation time); ② frontend refresh chain: gateway:user-message-saved (count +1, consistent with backend increment_messages) / gateway:message-complete (count unchanged) → chat.ts touchConversation updates locally; on list reload, the backend last_message_at is authoritative; ③ the switch-session-during-streaming case relies on the session_id in both event payloads for targeting (don't revert to sessionIdRef — it points at the wrong object after switching); ④ meta strings are uniformly built via chat.ts buildMeta() (new update points must use it, or date/count drift); ⑤ an empty conversation's last_message_at=NULL; the frontend falls back to started_at
21. **Notification sound covers two scenarios (2026-10-02)**: ① playCompletionSound() is now triggered from two places — message.complete (non-interrupted, original) and clarify.request (when the AI calls ask_user_question, added at the tail of the gateway.ts clarify.request branch); ② both share one setting set (localStorage pebble:completion-sound, SoundSelect panel); both silent when Off; ③ the SoundSelect panel copy was updated from "Completion sound" to "Notification sound"; ④ troubleshooting "no sound on questions": setting Off / no user gesture on the page (AudioContext not activated, silent failure, same cause as the completion sound); ⑤ the backend's only clarify.request send point is the ask_question branch in gateway/server.py

22. **WebSocket large-message limit + reconnect-state fix (2026-10-03)**: ① root cause: ws_server.py's websockets.serve() left max_size at the library default 1 MiB — image base64 inflates by 4/3, so an original image above ~768KB made the whole message exceed the limit; the server closed the connection at the protocol layer with code 1009 and the message never reached the business layer (diagnosis: that session in sessions.db has message_count=0 and no message rows, title not updated; backend log [WS] Connection closed code=1009); ② frontend amplification: on disconnect onStatus didn't clear streaming → the UI stuck at "Agent is responding..." forever and InputArea send() was blocked by streaming, so the user couldn't resend; ③ fix trio: serve(max_size=None) removes the limit entirely (isolated test: default config reproduces 1009 with 2MiB; None config sends/receives 2MiB fine), gatewayClient.sendMessage returns boolean (not connected/exception → false, no more silent drops), gateway.ts failPendingStream() marks Error and resets stream state at both onStatus(false) and send failure; ④ for similar "sent a message, nothing happens": first check sessions.db message_count to see whether the message reached the business layer, then check the backend for 1009 logs; ⑤ the frontend still keeps the 10MB/20-file attachment cap (unchanged); LLM API body limits (e.g. DeepSeek 48MiB) are downstream constraints, and API errors display normally when exceeded (no more silent freeze)

23. **ask_user_question multi-question pipeline fix (2026-10-15)**: ① root cause: the tool schema supports 1-4 questions, but the event/answer pipeline was a single-question-era leftover — server.py clarify.request sent only questions[0], _submit_clarify_answer hardcoded `{"answers":{"0":answer}}` → the UI showed only the 1st question while the agent received the full questions + a single answer (symptom: the agent asked 2 questions, the UI showed 1); ② fix (5 places, dual-channel compatible): server.py ask_question event sends the full questions array (single-question fields kept for compatibility); gateway.ts clarify.request consumes the array preferentially, falls back to single fields; gateway.ts ask-question-submit carries a structured answers object (HTML comments merged into the matching answer key); server.py clarify.respond accepts an answers parameter and _submit_clarify_answer is dual-channel (new: object pass-through / old: `{"0":...}` wrapping); ③ the frontend AskQuestionCard already supported multiple questions (rendering + answer-all guard), no change needed; ④ the recovery path (rebuild from output.questions) already mapped all questions, now consistent with the live path; ⑤ verification: isolated tests 9/9 (dual channel + request_id/no-pending guards + end-to-end format) + vue-tsc; ⑥ troubleshooting: partial multi-question card display → check the clarify.request payload for the questions array; the agent complaining "not answered" → check the answers keys (new = question text / old = "0")
