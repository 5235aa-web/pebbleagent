### Notes

4. **Provider loading**: `loadProvidersFromBackend` is called during app startup (2026-07)
8. **clarify second call**: with multiple asks in one turn, the frontend's `clarify.request` replaces `streamingMessage.questionCard` each time (id changes, render position does not). MessageBubble.vue binds `:key="message.questionCard.id"` on both AskQuestionCard usages; the component instance is rebuilt per question. A cancelled tool's empty `input` in execution_order means the tool_orchestrator cancellation event omits input, not that the LLM returned empty arguments
9. **Resume render order**: server.py saves assistant messages using `chat_completed_data.execution_order` (full R/X/T interleaved order); sessions.db's `messages.tool_calls` stores a bare tool array (`tool_executions`) and is only a fallback. agent_chat.db's `execution_order` holds the authoritative order. The frontend restores from sessions.db first (`resumeSession → convertBackendMessages`); a bare tool array triggers `text_fallback` at the end and `reasoning_fallback` at the front
12. **Image detail level**: ① the frontend InputArea selector Auto/Low/Orig shows only with image attachments; Auto = field not sent (documented as equivalent to original); ② detail flows AttachmentItem.detail → sendMessage serialization → server.py pass-through → service whitelist injection into the image_url block (invalid values silently ignored, fall back to the original image); ③ detail is a per-request parameter, not persisted (images never enter the DB); ④ low = 512×512 downscale, saves tokens; prefer it for OCR/screenshot scenarios; ⑤ the global selector applies to all images in the request (the docs support per-image detail; the current implementation uses one level for all)
13. **Images across sessions**: ① images are request-scoped and do not enter the DB (the service sends them per request; sessions.db messages has no attachments column); ② mergeCachedAttachments merges attachments of image-carrying user messages from the localStorage cache back into converted, matched precisely by messageId (not positional alignment); ③ limitation: depends on local localStorage — clearing the cache or another device loses the displayed attachment; ④ the model context has no image after restore (DB-restored history has no image_url block), so follow-up questions about the image need backend replay
14. **Question-card state**: ① submit/skip writes back to the message immediately (gateway markQuestionState sets questionCard.state = answered/skipped on the matching message, scanning both streaming and history); ② AskQuestionCard watches p.state and syncs its local sb/sk; ③ server-side guard: _submit_clarify_answer validates request_id == QuestionManager pending id; no pending / mismatch is ignored; ④ the event's request_id and the pending id are the same uuid (service set_pending_questions), so normal answers are unaffected; ⑤ the refresh-recovery path rebuilds answered/skipped consistently
15. **Question-card inline rendering**: the card is an inline question element inside executionOrder — when clarify.request arrives, the tail of order is exactly the clarify tool card (tool.call_streaming enters the stream first); the push lands right after the tool card; after answering, the agent's continued text/tool output appends below the element, and the card stays in place and is not pinned to the message end; chat_completed does not migrate questionCard (it is inline in eo); the recovery path splices a read-only card after the ask tool item in execOrder; MessageBubble renders the question branch + hasQInline dedup (fallback questionCard for older messages); markQuestionState dual-carrier (inline element + message-level). Note: the ask tool's output is still persisted in the DB; the question element is a pure frontend concept and does not enter the DB; recovery rebuilds from output.questions; the mechanism is frontend-only
16. **Streaming-highlight incremental rendering**: ① during streaming, ToolExecutionCard delegates to the utils/incrementalHighlight.ts engine — prefix region cached (recomputed only when S advances) + window region recomputed O(W) per chunk, a forged prefix reproduces the cut-point state (hljs prefix determinism guarantees visual equivalence); per-chunk real-time rendering, highlighting preserved, no throttling; ② whitelist: python/javascript/typescript/json/bash/plaintext; **css not included** (hljs's css strings are "fully-matching", the forged prefix doesn't work in unclosed streaming states); ③ known limitation: syntax-level nesting (hljs-params nesting depth of unclosed brackets) may show slight visual differences in intermediate states for "malformed text + specific cut points" — the completion state rebuilds fully and corrects it; differential tests pass on real-code scenarios; ④ when the engine is disabled/supported=false it falls back to full rendering (symptom = performance regression but correct display); check ToolExecutionCard's incActive state; ⑤ when extending languages: the scanner must handle "cross-window escape skipping" (the scanStateAt first-char skip logic) and pass differential tests
19. **Conversation-list time semantics**: ① a list entry's date = the conversation's latest message time (last row's created_at by sort_order in the messages table), not sessions.updated_at or started_at; ② frontend refresh chain: gateway:user-message-saved (count +1, consistent with backend increment_messages) / gateway:message-complete (count unchanged) → chat.ts touchConversation updates locally; on list reload, the backend last_message_at is authoritative; ③ the switch-session-during-streaming case relies on the session_id in both event payloads for targeting (sessionIdRef points at the wrong object after switching); ④ meta strings are uniformly built via chat.ts buildMeta (all update points reuse it, keeping dates and counts consistent); ⑤ an empty conversation's last_message_at=NULL; the frontend falls back to started_at
21. **Notification sound covers two scenarios**: ① playCompletionSound is triggered from two places: message.complete (non-interrupted) and clarify.request (gateway.ts clarify.request branch); ② both share one setting set (localStorage pebble:completion-sound, SoundSelect panel); both silent when Off; ③ the SoundSelect panel copy reads "Notification sound"; ④ troubleshooting "no sound on questions": setting Off / no user gesture on the page (AudioContext not activated, silent failure, same cause as the completion sound); ⑤ the backend's only clarify.request send point is the ask_question branch in gateway/server.py

22. **WebSocket payloads & reconnect state**: ① ws_server.py serve max_size=128MiB plus explicit prompt payload limits (text ≤2M chars; ≤20 attachments, ≤14MB each, ≤100MB total → prompt.rejected); ② gatewayClient.sendMessage returns boolean (not connected/exception → false); ③ gateway.ts failPendingStream marks Error and resets stream state at both onStatus(false) and send failure; ④ troubleshooting "sent a message, nothing happens": check sessions.db message_count to see whether the message reached the business layer, then check the backend log; ⑤ the frontend keeps the 10MB/20-file attachment cap (product design); LLM API body limits (e.g. DeepSeek 48MiB) are downstream constraints, and API errors display normally when exceeded

23. **Multi-question pipeline**: ① server.py ask_question event sends the full questions array (single-question fields remain for compatibility); ② gateway.ts clarify.request consumes the array preferentially, falls back to single fields; ③ ask-question-submit carries a structured answers object (HTML comments merged into the matching answer key); ④ server.py clarify.respond accepts an answers parameter; _submit_clarify_answer is dual-channel (object pass-through / single-answer form: `{"0":...}` wrapping); ⑤ the recovery path (rebuild from output.questions) maps all questions consistently with the live path; ⑥ troubleshooting: partial card display → check the clarify.request payload for the questions array; the agent reporting "not answered" → check the answers keys (question text / compatibility key = "0")

24. **Preview sandbox & WS auth**: ① gateway WS auth — the backend token (~/.pebble/gateway.token) reaches the dev browser via a vite transformIndexHtml plugin injecting window.__PEBBLE_GATEWAY_TOKEN__ (read fresh per page load); the Tauri build uses the get_gateway_token Rust command; gatewayClient appends ?token= to the WS URL; ② preview sandbox — HtmlPreview's iframe runs with sandbox="allow-scripts" only (no allow-same-origin → opaque origin); srcdoc is assembled by buildSrcdoc = injected meta CSP (connect-src 'none', frame-src 'none', form-action 'none'; https: kept for CDN scripts/styles/images) + inlined preview bridge (height reporting / PNG capture via html-to-image UMD / feedback CSS + theme vars) + feedback engine; all host↔preview traffic is postMessage with source-window checks; PNG export executes inside the iframe and returns a dataURL; ③ SVG preview is DOMPurify-sanitized before v-html (script/foreignObject forbidden; on* handlers stripped by default); MermaidCard securityLevel strict; ④ Tauri CSP + devCsp set in tauri.conf.json — script/style keep 'unsafe-inline'; the srcdoc preview inherits the host policy (all v-html injection points are sanitized, see ③); ⑤ troubleshooting: preview blank → check the meta CSP / bridge injection in the srcdoc; PNG "failed" → capture timeout (15s) or the inlined library missing; dev "auth rejected" (close 4401) → the token file was rotated or the backend just started (refresh the page)
